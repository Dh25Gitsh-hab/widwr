# ML workflow: correcting the wind forecast and predicting shortfall risk

This is the optional ML extension on top of the forecast-evaluation product. It covers how the data was validated, how one leakage-free dataset was built, how the models were trained and compared, and what the results do and do not show.

## Reproduce everything (from the `backend/` folder, venv active)

```bash
python -m ml.build_dataset   # validate the raw files, then build ml/processed/ml_dataset.csv  (~3 s)
python -m ml.train           # train, compare, evaluate and save models and reports           (~40 s)
pytest                       # 125 tests, including the leakage tests
```

The raw files in `DATASETS/` and `DATASETS1/` are **read only and never modified**. Every output is regenerated by these two commands. All models use fixed random seeds, so a rerun gives identical numbers.

| Output | Content |
| --- | --- |
| `ml/reports/data_validation.json` | Per-file and combined validation checks |
| `ml/reports/dataset_summary.json` | Rows kept and excluded (and why), split sizes, feature list |
| `ml/processed/ml_dataset.csv` | **The clean dataset**: one row per delivery hour, with IDs, 9 features, labels and split |
| `ml/models/error_regressor.joblib` | Selected regression model (with its feature list and training dates) |
| `ml/models/shortfall_classifier.joblib` | Selected classification model |
| `ml/reports/metrics.json` | Every candidate's validation and test scores, confidence interval, calibration and feature importance |
| `ml/predictions/test_predictions.csv` | Hour-by-hour January predictions of every candidate |

**What the API serves.** There are two separate prediction components, and each loads its own artifacts:

| Component | Default (approved) | Comparison | Endpoint |
| --- | --- | --- | --- |
| Corrected forecast | linear correction (`holdout_feb2026/models/regression_linear_by_level.joblib`) | Random Forest (`models/error_regressor.joblib`) | `GET /api/ml/corrected-forecast` |
| Shortfall risk | logistic regression (`holdout_feb2026/models/classification_logistic_by_level.joblib`) | Random Forest (`models/shortfall_classifier.joblib`) | `GET /api/ml/shortfall-risk` |

**Model selection decision (approved 2026-10-26).** The linear correction and the logistic model are the selected defaults for the current application, and the two Random Forests remain available as comparison models.

- **History:**
  1. The rule fixed before January (lowest December validation error, section 6) chose the Random Forest for both tasks.
  2. The January test then favoured the linear correction, so January had shaped the preference.
  3. That preference was re-tested offline on February 2026 (section 8).
  4. The defaults were approved on 2026-10-26.

  The **choice** therefore reflects evidence from after the January decisions. The prediction inputs and model weights do not: they use only data published before each cutoff and up to 31 Dec 2025.
- **Basis:** in the February check, the linear correction was the only model clearly better than the official forecast (−36% MAE, with a 95% interval that excludes zero), and the logistic model gave the better-calibrated shortfall probabilities.
- **Scope:** the application covers January 2026 decisions only and never loads February data or results. `GET /api/ml/models` shows January test scores and `selected_by_pre_january_rule`.
- **Safeguards still in force:** the 09:50 cutoff check, no label inputs, and artifact fingerprints checked against the holdout seal.
- **What it is not:**
  - It is a selection on two winter months, not proof that these models will stay better.
  - It does not show that the linear correction beats the Random Forest; that comparison was inconclusive.
  - It is not evidence of trading profit.

The other endpoints:

- `GET /api/ml/predictions` combines both components in one call.
- `GET /api/ml/models` lists every served model with its role, inputs, artifact fingerprint and scores.
- `GET /api/ml/evaluate` returns the January comparison below.

No model was retrained to serve them.

## 1. Files found and validation results

| Folder | File | Records | Content |
| --- | --- | --- | --- |
| `DATASETS/` | `Oct25_Actual.json` | 1,490 | FUELHH wind, settlement days 1–31 Oct 2025 (26 Oct has 50 half-hours: clock change) |
| | `Nov25_Actual.json` | 1,440 | 1–30 Nov 2025 |
| | `Dec25_Actual.json` | 1,488 | 1–31 Dec 2025 |
| | `Jan26_Actual.json` | 1,488 | **2 Jan – 1 Feb 2026** (1 Jan is not included) |
| `DATASETS1/` | `Oct25_Forecast.json` | 18,128 | WINDFOR, 248 runs published 1–31 Oct 2025 |
| | `Nov25_Forecast.json` | 17,520 | 240 runs, Nov 2025 |
| | `Dec25_Forecast.json` | 18,104 | 248 runs, Dec 2025 |
| | `Jan26_Forecast.json` | 18,104 | 248 runs, Jan 2026 |

**Every check passed:**

- **Formats:** each file is a JSON list of Elexon records, with ISO-8601 UTC timestamps (`...Z`) and integer MW.
- **Values:** no nulls, no non-numeric values, no negatives.
- **Duplicates:** none, either within a file or across files.
- **Settlement calendar:** `settlementDate` equals the UK-local date of `startTime` for 100% of actual records.
- **Run structure:** every forecast target is on the hour (WINDFOR is hourly), and every run has 73 or 74 values.

There are two warnings, both handled by **excluding** the affected hours. Nothing is filled in.

| Warning | Effect |
| --- | --- |
| **Actuals for 1 Jan 2026 are missing** (48 half-hours): the January file starts on 2 Jan | Delivery day 1 Jan cannot be scored, so it is excluded |
| **No forecast runs before 1 Oct 03:30 UTC** (September is not provided): 1 Oct has 7 runs | Delivery day 1 Oct has no decision-time forecast, so it is excluded |
| 26 Oct has 9 runs | Expected: that day is 25 hours long |

**Units:** both datasets report generation in **MW** (Elexon schema). The magnitudes agree (mean actual about 10.6 GW, mean forecast about 12.2 GW), so no conversion is needed.

## 2. Three different times: why they matter

| Time | Field | Meaning |
| --- | --- | --- |
| **Forecast publication time** | WINDFOR `publishTime` | When a forecast run became available. This decides whether it could be used for a decision |
| **Delivery (target) time** | `startTime` in both datasets | The hour (or half-hour) the power is generated and delivered. This is the key that joins forecast to actual |
| **Actual generation time and availability** | FUELHH `startTime` / `publishTime` | `startTime` is when the energy was generated; `publishTime` (about 30 min later) is when that actual value became *known* |

A forecast for 15 Jan 10:00 may have been published on 13, 14 or 15 Jan; there are about 20 versions. The decision for 15 Jan is made on **14 Jan at 09:50 UK time**, so only versions published by then may be used. Likewise, an actual value can only be used as a *feature* if it had been **published** by then.

## 3. Decision cutoff and DST

- **Cutoff:** 09:50 UK local time on D-1 (Nord Pool GB day-ahead gate closure), converted to UTC per day with `Europe/London`.
- **In BST (October):** the cutoff is 08:50 UTC. **In GMT:** it is 09:50 UTC.
- **Verified on the clock-change weekend:**
  - Delivery 26 Oct (a 25-hour day) is decided on 25 Oct at 08:50 UTC and uses the 08:30 UTC run.
  - Delivery 27 Oct is decided on 26 Oct at 09:50 UTC and uses the 09:30 UTC run.
- **Result:** for every delivery day that has a forecast (2 Oct – 1 Feb), the run used is the "09:30 UK time" run on D-1.

**Is the publication history sufficient?** Yes. All 984 runs carry their own `publishTime` (8 per day; 7 on 1 Oct and 9 on the clock-change day), so the cutoff can be verified for every single hour. Nothing has to be assumed.

## 4. Multiple forecast versions and leakage prevention

- **Choosing among versions:** for each delivery hour, the selected forecast is the latest version with `publishTime ≤ cutoff`. This uses the API's own `latest_forecast_as_of` (`pandas.merge_asof`), so the API and the ML use the identical rule.
- **Values that are not forecasts:** each WINDFOR run also repeats hours that had already started when it was published. Those 15,170 values are removed during cleaning.

**Features** (`app/services/feature_builder.py`). Each one uses only data published by the cutoff.

| Feature | Meaning |
| --- | --- |
| `forecast_mw` | Official forecast for the hour: latest version published by the cutoff |
| `lead_hours` | Hours between that version's publication and the target hour |
| `hour_uk` | UK clock hour |
| `forecast_revision_mw` | Change versus the previous run for the same hour |
| `forecast_spread_mw` | Std-dev of all versions published in the 24 h before the cutoff (disagreement between runs) |
| `forecast_ramp_mw` | Change from the previous hour in the same run |
| `forecast_day_mean_mw` | Mean forecast over the delivery day |
| `latest_actual_mw` | Latest actual generation **already published** at the cutoff |
| `recent_error_mw` | Mean day-ahead error over the last 24 h whose actuals were **published** by the cutoff |

**Labels** (targets only, never inputs): `actual_mw`, `error_mw = forecast − actual`, `shortfall_1gw = error ≥ 1,000 MW`.

**Proven by tests** (`tests/test_feature_builder.py`):

- Overwriting every forecast published *after* the cutoff with 99,999 MW leaves all features identical.
- Overwriting every actual published after the cutoff leaves the features identical too; only the labels change.

## 5. The clean dataset and the split

There are 2,977 delivery hours from 1 Oct 2025 to 1 Feb 2026:

- 24 are excluded for having no decision-time forecast (1 Oct).
- 24 are excluded for having no actual (1 Jan).
- **2,929 rows remain.**

The split is **chronological, by the month the purchase decision is made**, and never shuffled:

| Split | Decisions | Delivery days | Hours | Shortfall ≥ 1 GW |
| --- | --- | --- | --- | --- |
| Train | Oct–Nov 2025 | 61 | 1,465 | 52% |
| Validation | Dec 2025 | 30 | 720 | 53% |
| **Test** | **Jan 2026** (the brief's scope) | 31 | 744 | **66%** |

**Protocol:**

1. Fit on train and score on validation, then select (lowest MAE for regression, lowest Brier score for classification). A baseline is allowed to win.
2. Refit on train + validation, then score **once** on test. Every candidate is reported on test, but selection never looks at it.

## 6. Models

**Regression**: predict the official forecast's error, then corrected forecast = forecast − predicted error. Scored with MAE and RMSE against actual generation, alongside the published forecast.

**Classification**: the probability that actual wind comes in **at least 1 GW below** the forecast. Scored with Brier score, ROC-AUC, PR-AUC, precision, recall, F1 and accuracy.

Candidates are tried simplest first:

| Regression | Classification |
| --- | --- |
| `official_forecast`: no correction (the published baseline) | `base_rate`: always the training frequency |
| `mean_bias`: subtract the average training error | `logistic_by_level`: logistic regression on forecast size |
| `linear_by_level`: linear correction by forecast size | `random_forest`: RandomForestClassifier, all features |
| `random_forest`: RandomForestRegressor, all features | `gradient_boosting`: HistGradientBoostingClassifier |
| `gradient_boosting`: HistGradientBoostingRegressor | |

Hyper-parameters are conservative (leaves of at least 20 samples, shallow boosting), because 91 days of training data is a small sample.

## 7. Results (January 2026 test set, 744 hours)

### Regression: corrected forecast vs actual (MW)

| Model | Validation MAE | **Test MAE** | Test RMSE | Test bias | vs official | Days better than official |
| --- | --- | --- | --- | --- | --- | --- |
| official_forecast (baseline) | 1,955 | 1,996 | 2,499 | +1,728 | – | – |
| mean_bias | 1,758 | 1,396 | 1,834 | +325 | −30.0% | 25 / 31 |
| **linear_by_level** | 1,327 | **1,179** | **1,535** | +31 | **−40.9%** | **26 / 31** |
| random_forest ← *selected on validation* | **1,034** | 1,381 | 1,740 | −22 | −30.8% | 20 / 31 |
| gradient_boosting | 1,112 | 1,551 | 1,912 | −89 | −22.3% | 16 / 31 |

- The selected Random Forest cuts January MAE by **614 MW**. The 95% confidence interval is **201 to 1,054 MW** (day-block bootstrap, 31 days), so the improvement is statistically clear.
- The simplest model generalised best. `linear_by_level` ("the forecast over-predicts more the more wind it forecasts") was the best on January.
- Random Forest won on validation, in both November and December when checked with rolling validation, but lost ground in January.
- Permutation importance explains why. On January, shuffling `forecast_mw` costs the Random Forest +245 MW of MAE, while shuffling `recent_error_mw`, `latest_actual_mw` or `forecast_day_mean_mw` makes it *better*. Those history patterns held in Oct–Dec but not in January, where the shortfall rate jumped from 53% to 66%. The forecast-size effect is the stable signal.

### Classification: P(shortfall ≥ 1 GW)

| Model | Validation Brier | **Test Brier** | ROC-AUC | PR-AUC | Accuracy | Precision | Recall | F1 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| base_rate (baseline) | 0.249 | 0.243 | 0.500 | 0.660 | 0.660 | 0.660 | 1.000 | 0.795 |
| **logistic_by_level** | 0.158 | **0.202** | **0.755** | **0.874** | 0.667 | **0.778** | 0.693 | 0.733 |
| random_forest ← *selected* | **0.131** | 0.221 | 0.723 | 0.864 | 0.665 | 0.757 | 0.725 | 0.741 |
| gradient_boosting | 0.151 | 0.245 | 0.727 | 0.865 | 0.663 | 0.748 | 0.737 | 0.743 |

Reading this honestly:

- **Accuracy is not the right measure here.** In January, 66% of hours had a shortfall, so "always predict shortfall" already scores 66.0% accuracy and F1 0.795. At a 0.5 threshold the models barely beat it on accuracy (0.663–0.667) and do worse on F1.
- **What the models do add is ranking and probabilities.** ROC-AUC is 0.72–0.76, and the Brier score is better than the base rate. The 0.8–1.0 band is reliable: the predicted 96.5% happened 91.4% of the time (267 hours).
- **Low probabilities are not reliable in January.** Hours given 0–20% (mean 12%) actually had shortfalls 56% of the time (112 hours). Low-risk readings should therefore be treated with caution until the model is recalibrated on more recent data.

## 8. February 2026 fresh holdout (independent re-test)

> **Scope note:** this is offline, supplementary evidence outside the assignment's January-only scope. The application does not load these data or results; they informed only the choice of default models (see "Model selection decision" above).

January informed the "linear vs Random Forest" question, so both models were frozen and re-tested on **February 2026**. Their predictions were sealed (SHA-256) before any February actual was read. The full protocol and results are in [holdout_feb2026/README.md](holdout_feb2026/README.md). In short, over 648 hours and 27 days:

| | MAE (MW) | vs official |
| --- | --- | --- |
| Official forecast | 1,693 | – |
| Random Forest | 1,298 | −23% (95% CI of the gain includes zero, just) |
| Linear correction | **1,082** | **−36% (significant: 290–955 MW gain)** |

- Random Forest vs linear is **inconclusive**: a 216 MW gap favouring linear, but the 95% CI is [−64, +491].
- For shortfall risk, the logistic model was better calibrated than the Random Forest, whose probabilities showed almost no skill over the base rate.

The training pipeline reads only the Oct 2025 – Jan 2026 files (`TRAINING_MONTHS` in `build_dataset.py`), so the February files can never leak into training.

## 9. Limitations and what more data would help

- **Sample size.** There are 61 days for model selection, 91 for the final fit and 31 for testing. Hours within a day are correlated, so the effective sample is closer to the number of days. More months, including other seasons, would make both the training and the comparison more reliable.
- **One season only.** The data is autumn and winter. Nothing here supports use in spring or summer without retraining on those months.
- **Distribution shift.** January had more and larger shortfalls than Oct–Dec. A model in production should be retrained regularly, for example monthly on a rolling window.
- **A fresh test set.** Done for February 2026 (section 8). A month is still short; ongoing monthly re-evaluation is the real safeguard.
- **Missing drivers.** The likely cause of the bias (curtailment of wind on high-output days) is not in the data. Curtailment or constraint data would probably be the most valuable addition.
- **Data gaps.** 1 Jan 2026 actuals are missing from the provided files. For the 2 Jan decision, the history features therefore come from 31 Dec, which is older than usual.
- **No trading claims.** Forecast accuracy is not trading profit. There are no prices, imbalance costs or volumes in scope, so **no claim about trading performance or profitability is made.**
